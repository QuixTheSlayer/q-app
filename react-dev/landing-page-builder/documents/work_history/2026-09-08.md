## Thumbnail capture: html2canvas → real screen capture → back to html2canvas

**What:** Replaced html2canvas with `getDisplayMedia()`-based screen capture for both the full-page thumbnail and sub-template capture flows (`fd1ce26cd`), then reverted it the same day (`d012fe974`).

**Why:** html2canvas re-implements CSS painting itself and diverges from what the browser actually renders (gradients, fonts, shadows, flex/grid). `getDisplayMedia` fixed that accuracy problem but introduced a worse one: the browser's native picker lets the user select their entire screen or an unrelated window instead of just the target element — disqualifying for a feature meant to silently produce a thumbnail.

**How (final state):** `captureHtml2Canvas.ts` (`captureElementAsPng`) inlines S3 images as base64 first (`convertToCanvas.ts` now inlines `<img>` tags the same way background-images already were, avoiding html2canvas's own cross-origin image fetch), then runs html2canvas directly on the real, live element — no offscreen clone, no forced `fit-content`/zoom overrides, so it can't diverge from on-screen layout the way the original implementation did. `s3DevProxy.ts`'s `toUploadUrl` was renamed `toS3DevProxyUrl` and applied to these image-inlining fetches too, not just the upload PUT, since reading images back for capture hits the same S3 CORS wall on GET. Dropped the `isCapturing` on-screen dance and permission-prompt toasts `getDisplayMedia` needed; `captureViaDisplayMedia.ts` and `PreviewContext`'s `isCapturing` were deleted as no longer used.

Along the way, pulled `Editor.page.tsx`'s save logic (plan-tier check/warning, dev/prod payload shape, sync-status tracking, localStorage draft cleanup) into a shared `useSavePageData.ts` hook with an `overrides` param, so Canvas.tsx's post-capture save goes through the same path instead of a thinner, unawaited one — and now takes `title` as a prop instead of reading it from Redux, which went stale on every keystroke since title edits never dispatched back to the store. Dead leftover capture code in `Editor.page.tsx` (`uploading` state, `useUploadToS3` call, `sectionCount`, `getCanvasBlob`) was removed as unused (`cf3c06fdf`).

`documents/thumbnail-capture.md` was rewritten to document all three approaches tried (cloned html2canvas → server-side Browsershot → getDisplayMedia → in-place html2canvas) and why each was set aside — see that doc for the full comparison.

## Dev-host fixes (`local.newjudgify.me:5173` via Vite)

**What:** Several issues surfaced only when testing through the Vite dev host instead of the vhost directly:
- Proxied `generate_upload_url`/`genereate_signed_url` to the real backend and added a `/s3-dev-proxy` passthrough to S3, so presigned-URL upload PUTs stay same-origin instead of hitting the bucket's CORS policy (which only allows the vhost origin).
- Added `local.newjudgify.me` to Vite's `allowedHosts` (its DNS-rebinding protection otherwise blocks it outright).
- `axiosCsrf.ts` now explicitly attaches the `XSRF-TOKEN` cookie as `X-XSRF-TOKEN` on every request — Vite's dev `index.html` has no CSRF meta tag, and axios's automatic same-origin XSRF detection wasn't firing reliably through the proxy layer.
- `Canvas.tsx`: page-thumbnail upload now uses a fixed `subFolder` instead of an empty one — an empty subfolder built the S3 key as `{user_id}//{filename}`, which the Vite proxy normalizes to a single slash, breaking the presigned URL's signature match.
- `routes.json`: mapped `/landing-page-builder/subtemplates` to the existing `my-components` json-server resource, since `query.ts` calls it `subtemplates` (matching the real Laravel route name) but the mock only had `my-components`.
