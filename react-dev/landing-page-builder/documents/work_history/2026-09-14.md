# Session Log — 2026-09-14

Built an end-to-end Playwright walkthrough of the landing page builder for a user guide (screen-recorded), covering both click-based and real drag-and-drop content insertion.

## Playwright suite (isolated worktree)

**What:** New `playwright.config.ts` + `playwright-test/builder-walkthrough.spec.ts` + `playwright-test/dom.utils.ts` on a branch that had no Playwright suite of its own yet. Video and HTML report output point outside the repo (`C:\wamp64\www\e2e-recordings\landing-page-builder\`).

**Why:** Asked for a detailed, user-friendly end-to-end UI test of the builder, recorded as a video for a user guide, with the recording kept out of the project folder so it doesn't pollute git status or get committed by accident.

**How:** Started from a plain click-driven walkthrough (Section → Block → Text/Image/Button → edit → save → preview) and iterated against the real running app — this is a custom drag-and-drop editor with no `data-testid`s anywhere, so every locator had to be derived from actual DOM/accessibility inspection rather than assumption. Took ~10 iterations to go green, surfacing several real findings along the way:

- **`webServer` startup race.**
  - *What:* Playwright's readiness check only polled Vite (port 5173).
  - *Why it mattered:* `npm run dev` also starts json-server (port 3000) concurrently — the app's actual data backend. Under load, the editor's very first render could fire its data fetch before json-server had finished binding its port, and RTK Query doesn't retry on failure, so the editor got stuck on a blank shell forever.
  - *Fix:* Pointed the readiness check at json-server's own data endpoint instead of Vite's, so the test suite won't start until both are actually serving.

- **Insert-panel buttons' accessible name includes their shortcut badge.**
  - *What:* `getByRole('button', { name: 'Section' })` never matched.
  - *Why:* The keyboard-shortcut hint ("/ + S") renders as visible text inside the same `<button>`, ahead of the label, so the real accessible name is `"/ + S Section"`.
  - *Fix:* Built the expected name from the shortcut letter + label instead of assuming just the label.

- **An always-mounted offscreen preview clone duplicates every `data-id`.**
  - *What:* Locators like `[data-id="..."]` resolved to two elements instead of one.
  - *Why:* `Canvas.tsx` keeps a `top:-999999px` clone of the currently-focused node (for a hover-preview thumbnail, rendered via `PreviewUI/Elements`), and it carries the exact same `data-id`/`data-node-path` as the real, interactive node.
  - *Fix:* Scoped every node lookup to `[data-canvas-root]` (the real canvas), which the offscreen clone lives outside of.

- **`aria-disabled` on drag-disabled nodes reads as "not clickable" to Playwright.**
  - *What:* Plain `.click()` on a section/root node timed out waiting for it to become "enabled".
  - *Why:* dnd-kit sets `aria-disabled="true"` on sections/root purely to mark them non-draggable (drag-reorder is intentionally disabled for those) — semantically unrelated to whether they're clickable, but Playwright's actionability check doesn't know that.
  - *Fix:* Added `force: true` to canvas-node clicks.

- **Focusing a node doesn't switch the sidebar to the Properties view.**
  - *What:* Clicking a node and then asserting "Section Properties" is visible failed.
  - *Why:* The left sidebar has an independent, icon-only toggle between the Insert/Layers panel and the Properties panel with no text or `aria-label` on this branch — a real user has to click the gear icon separately.
  - *Fix:* Located the toggle via its (unique in this app) `Settings2Icon` lucide CSS class and clicked it explicitly wherever a Properties check was needed.

- **Dragging an existing node onto a sibling to reorder it duplicated content instead of moving it.**
  - *What:* A drag-reorder step grew the Block from 3 children to 4 rather than just reordering the existing 3.
  - *Why:* Either a real bug in this app's move-vs-insert drag handling, or an artifact of simulating raw mouse events for that specific "existing node onto existing node" case — confirmed via a before/after `data-node-path` dump, not guessed.
  - *Decision:* Dropped the step rather than ship something flaky/data-corrupting in a suite that doubles as a recorded user guide — it also wasn't what was actually asked for (dragging *new* elements from the Insert panel into sections/blocks was the ask, not reordering existing ones).

- **Mobile preview width hangs.**
  - *What:* Clicking "Preview mobile view" hung well past any reasonable timeout on this ~2-dozen-node sample page.
  - *Why:* Every canvas node has a Framer Motion layout animation; collapsing to mobile width re-triggers it across the whole tree at once.
  - *Decision:* Dropped from the walkthrough, kept desktop↔tablet (exercises the same responsive-preview feature without the reflow storm).

**Result:** Full pipeline — click-insert Section → drag-insert Block onto the Section → drag-insert Text onto the Block → click-insert Image/Button → edit text inline → check Image/Button property panels → rename + bold the Button → check Layers panel → preview at tablet width → Save → verify on the live Preview page. Passed clean in 1.5–4.6 min depending on run. Committed as `9e3fa0328`.

## Extending the *actual* suite (main checkout, branch `landing-playwright-test`)

**What:** One new spec file added on top of an existing, more mature Playwright suite discovered mid-session on the user's actual working branch.

**Why:** The user pointed out the walkthrough above only existed in an isolated worktree, not their working copy, and asked for it to end up in their actual codebase. `landing-playwright-test` turned out to already have its own suite (`playwright-test/editor/{fixtures,insert-panel,canvas-and-property-panel,layers-panel,save-and-preview,top-bar,undo-redo-zoom}.spec.ts`) with proper `aria-label`s on the panel toggle (`"Open Property panel"` / `"Open Insert panel"` — the icon-hack from the worktree section above wasn't needed here), Layers-panel-based node identification (avoids a documented WebKit portal-ordering issue), and a `blockSaveRequests` fixture that intercepts `save/:id` so tests never mutate the shared dev `db.json`. A blind branch merge would have conflicted badly: `package-lock.json` alone had a ~30,800-line diff from two independently-run `npm install`s, plus add/add conflicts on `playwright.config.ts`/`.gitignore`/`package.json`.

**How:** Rather than merge branches, added `playwright-test/editor/drag-and-drop-walkthrough.spec.ts`, reusing the existing suite's fixtures instead of re-deriving them, leaving every existing file untouched. Inserts a Section, a focused Block inside it, then Text/Image/Button; edits the text inline; checks each element's Property panel; renames + bolds the Button; checks the Layers panel; saves (mocked); confirms Preview loads. `video: 'on'` scoped to just this file via `test.use()`; run standalone with `--output=<dir outside the repo>` to keep the shared config untouched.

This file went through many more iterations than the worktree version above, surfacing several additional real findings — some initially misdiagnosed before the actual cause was found:

- **Real drag-and-drop turned out to be unreliably flaky here, not just occasionally slow.**
  - *What:* Dragging a "New" (Insert-panel) element onto a small or edge-adjacent canvas target intermittently misclassified which edge the cursor was nearest to.
  - *Why:* `useCanvasDnd.ts`'s `processDragMove` / `dnd.utils.ts`'s `getNearestEdge` uses a fixed 10px-from-edge threshold, not a percentage — for a small target (e.g. an empty Block, ~200px tall) or when the canvas auto-scrolled mid-drag, a coordinate that was fine for a large target could land past that threshold and route the insert to the wrong parent, or the app's own drop-position ref could end up unset even though dnd-kit's own "was dropped over droppable area X" announcement fired. Confirmed via direct logging of the app's internal `over.rect`/`currentX`/`currentY` state across several runs — the failure mode changed between runs of *identical* code, and even a "passing" run could be verified (via a direct `data-node-path` check) to have placed the node as a root-level sibling instead of nested inside the intended container.
  - *Decision:* Not a test-side problem a workaround could reliably paper over. Deleted the raw-mouse-drag helper (`drag.utils.ts`) and rewrote the spec to use click-based insertion instead, matching `insert-panel.spec.ts`'s already-proven pattern (every Insert-panel button inserts into the focused container on a plain click — dragging is one way in, not the only way).

- **Two theories for a long-standing "click on the Insert tab hangs forever" failure, only the second one right.**
  - *First (wrong) theory:* Assumed a floating quick-edit popover (`PopoverWrapper.tsx`/`ActionMenu.tsx`) that opens whenever a canvas node is focused was left open and blocking clicks elsewhere; tried dismissing it with Escape (didn't work) and then a click-outside-canvas technique (seemed to work, but was actually masking the real bug by clearing focus at the same time — see below).
  - *Actual cause:* `openPropertyPanel`/`openContentPanel` (fixtures.ts) toggle the sidebar's **outer** view — switching to Property view fully unmounts `ContentPanel`, including its own **inner** Insert/Layers/Sub-Templates tab strip. `openInsertTab`/`openLayersTab` operate on that inner strip and only work while the outer view is already "content". The spec was calling `openInsertTab` right after `openPropertyPanel` with no outer switch back in between, so the tab it was waiting for simply didn't exist in the DOM — Playwright waited the full timeout for an element that was never coming.
  - *Fix:* Added `openContentPanel()` calls at every point the flow returns from a property check to inserting/checking the Layers panel.

- **`insertButton('Button')` is ambiguous.**
  - *What:* `fixtures.ts`'s shared `insertButton` helper matches a button's accessible name as a trailing substring (to tolerate the "/ + N " shortcut-badge prefix) — for the label "Button" specifically, that also matches "Submit Entry Button" and "Register Button", a 3-way strict-mode violation. None of the suite's existing specs happened to call `insertButton(page, 'Button')` for the plain content type before, so this was never exposed.
  - *Fix:* Used an exact-name `Locator` for that one call site instead of the shared helper's label-string form.

- **Typing into the freshly-inserted text node silently did nothing — same root cause as the worktree section's text-edit bug, found independently a second time.**
  - *What:* `Ctrl+A` + typed text never appeared; the node still showed its default placeholder.
  - *Why:* Calling `openPropertyPanel(page)` between focusing the text node and typing clicks a sidebar button, moving keyboard focus off the node's contentEditable before the keystrokes arrive.
  - *Fix:* Reordered to click the node, type immediately, and only afterward open the Property panel to verify — matching the same fix already applied in the worktree suite's version of this same interaction.

**Result:** Full pipeline passed in 1.6 min: insert Section/Block/Text/Image/Button via click → edit text inline → check Image/Button property panels → rename + bold the Button → check Layers panel → Save (mocked) → confirm Preview loads.
